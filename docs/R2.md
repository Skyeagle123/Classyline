# R2 cart consistency and coordinated recovery

Base: `ec6df6e555eb1bd5aa902daa84678b4e3173751b`. Scope: R2-01, R2-02, R2-03.

## Shared cart and consumption

`CL_CART_V4` is one atomic browser-storage record containing a schema version,
random cart version, product/quantity lots and a pending/consumed checkout journal.
It contains no customer name, phone or address. Every explicit Add creates a new
lot ID; the checkout snapshot records those exact IDs and the cart version.
Cross-tab storage events, same-tab change events and focus reconciliation update
React views. React state never writes a stale cart back to storage.

Every cart edit, submission, receipt recovery and acknowledgement uses the same
`classyline-checkout` Web Lock. Submission reconciles shared storage, checks the
rendered cart version and exact aggregated items, then persists the key and bound
snapshot before POST. Missing Web Locks, inaccessible/malformed storage and failed
persistence stop checkout. Any uncertain response leaves the original key pending;
the existing server recovery/retirement API remains unchanged.

Receipt handling atomically marks the snapshot consumed and removes only its lot
IDs. Later additions, including the same variant and remove/re-add, have different
IDs and survive. Repeated recovery cannot consume twice. Acknowledgement advances
the shared version and clears only the attempt, never the bag. An interrupted
acknowledgement retains the journal even if the legacy key marker was already
removed; recovery and acknowledgement can finish safely.

After consumption, a fresh order requires explicit Add actions. A stale view cannot
reuse the consumed version or inject its old items with a fresh key. Cancelled
receipts also consume their client snapshot; ordering those products again requires
deliberately adding them. This does not create an order or change server inventory.

R1 pending keys have no trusted shared cart snapshot. Import their key, preserve
the unknown bag contents, recover the original receipt and require an explicit,
version-bound "Use this reviewed bag for a new order" action after acknowledgement.
Do not infer consumption from receipt titles or clear an unknown legacy bag.
Temporary contact payloads stay only in sessionStorage and are removed on resolution.

The protocol coordinates R2 tabs sharing one browser origin/storage partition.
It is not a server-enforced cross-device cart identity. R1/older already-open tabs
do not implement this protocol: before any future rollout, require those tabs to
reload/close and validate the upgrade flow. Do not silently downgrade the frontend
or clear recovery storage to resolve an uncertain checkout.

## R2-03: safe roll-forward recovery after migration 0002

There is **no down migration** and no remote database change in R2. Migration 0002
requires a reservation deadline on order insertion. Application `7175dce...` and
earlier are incompatible with that trigger. Reverting application files alone is
not an approved rollback. Frontend R1 also reintroduces the reviewed cart defects.

For a separately authorized staging/release rehearsal:

1. Record the exact application SHA, database identity, migration history and
   backup/bookmark. Verify the intended database explicitly; preserve orders,
   order items, retired keys, sessions and recovery evidence. Do not export PII to
   public logs/artifacts. Record in-flight/uncertain requests without exposing keys.
2. If a release fails, fail closed for **new** checkout admission using the
   deployment's approved maintenance mechanism. Do not assume that a network
   timeout means no order was committed. Keep browser pending keys and journals.
3. Retain schema 0002 and restore/roll forward to an independently verified
   schema-0002-compatible backend **and R2-compatible frontend**. If that artifact
   is unavailable, remain in maintenance; never substitute the incompatible parent.
4. Verify schema columns and triggers, database integrity, existing order/line
   snapshots, stock balances and retired-key evidence. Verify ordinary startup.
5. Recover exact pending keys through the compatible recovery endpoint. Check
   same-key replay returns the original receipt without reserving twice and retired
   missing attempts remain rejected. Recovery may intentionally add retirement
   evidence or expire overdue pending reservations; reconcile those transitions.
6. Reopen admission only after separately authorized D1/browser validation and
   review. Existing receipts and uncertain attempts must remain recoverable.

Never drop the deadline or retirement triggers, rewrite historic order keys,
purge recovery evidence, restore an old database over newer orders, or remove
columns to make an old application appear compatible. Any future database restore
requires its own data-reconciliation plan and approval.

`tests/rollback.test.js` rehearses this safe roll-forward path on synthetic local
SQLite: a post-0002 order and retired attempt exist; the exact parent insert shape
fails without data loss; the compatible application recovers the saved receipt,
same-key retry does not reserve twice, and the retired attempt stays rejected.
This proves local code/schema compatibility, not a deployment rollback execution.

## Validation limits

Tests cover consumed/stale tabs after merchant confirmation, parallel edits,
post-checkout additions, lost/delayed responses, remove/re-add, persistence and
acknowledgement failures, legacy recovery and explicit intent. No real browser,
Cloudflare D1 or deployment validation is claimed. D1 runtime limits, production
abuse controls, data retention, business decisions and independent final review
remain outstanding. No source changes outside this scope, new infrastructure or
live integration calls are authorized.
