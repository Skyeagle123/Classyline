# R3 checkout compatibility and recoverable cart errors

Base: `8d43b878e7c86b4310d8da33301b731c23ce01a2`. Scope: R3-01 and R3-02 only.

## Protocol barrier

New POST `/api/orders` requests require `X-Classyline-Checkout-Protocol: 2`.
The shared constant is imported by both the server and the versioned-cart client.
Existing order validation, idempotency hashes, atomic reservation, expiry and
stock triggers remain in place. The declaration is a compatibility barrier for
older application code, not authentication, bot protection or proof of customer
intent. A caller manually copying the header still faces the existing validations
but is not thereby proven to implement the cart protocol.

For a missing/new key with missing or unsupported protocol, respond HTTP 409 with
`code=CHECKOUT_UPGRADE_REQUIRED`, `required_protocol=2` and actionable instructions
to reload the page, review the bag and recover any earlier attempt. The gate runs
before expiry sweeps, admission counters, retirement writes and order/inventory
writes. Any key lookup preceding it is read-only. Do not automatically replace an
uncertain order key just because the user receives an upgrade message.

Existing saved keys are deliberately exempt from the new-submission barrier:
an identical-body same-key POST can retrieve its saved receipt without a protocol
header, and `/api/orders/recover` remains header-independent. Changed-body retries
remain rejected. Legitimate recovery still performs normal overdue reservation
expiry; that is separate from the non-mutating upgrade rejection for new attempts.
Missing-key recovery still atomically retires delayed attempts.

When an older R1/R2 tab tries a fresh key after a confirmed order, the backend now
rejects the request before any mutation. Its existing error rendering displays
the reload guidance. New client assets and compatible backend must be rolled out
together under separate deployment authorization; old code cannot be made current
by silently clearing browser state. No schema change is needed.

## Ordinary action errors versus fatal failures

Quantity and cart-size limits throw `CartActionError`. The provider's shared action
handler reconciles the authoritative cart under its Web Lock before classifying
the error as recoverable. It displays an action error while leaving healthy Add,
Remove and Checkout controls available. A successful action clears the error.

Storage, persistence, locking, corrupt-state and unexpected failures are fatal.
They keep controls disabled until a successful safe reconciliation. If storage or
locking fails while reconciling an ordinary error, that failure is fatal too.
Opening/recovering the bag explicitly reconciles provider health; React state
still never writes a stale cart back to storage. Receipt consumption and server
recovery semantics from R2 are unchanged.

## Validation and rollout limits

Regression tests cover unsupported/missing versions without any database write,
including an overdue reservation; confirmed-order legacy replay; existing-key
receipt compatibility; expired-key exactly-once release; missing-key retirement;
the client header; 21st-unit and 31st-variant errors followed by healthy actions;
and genuine storage/coordination failures. Tests use synthetic local SQLite and
injected storage/locks. They exercise the same action handler used by React but
do not constitute real browser rendering, native Web Locks or Cloudflare D1 tests.

No migration, deployment, paid resource, live order or live integration is used.
Independent review and separately authorized browser/D1 staging tests remain
required. Validate mixed-version tabs, background/frozen tabs, native storage
events, network abort/reload and the non-mutating response in the actual runtime.
The schema-0002 safe roll-forward procedure in `docs/R2.md` still applies; a
fallback backend must also enforce this protocol barrier before admitting new
orders. Broader production abuse controls, retention and business decisions
remain outside this narrow remediation.
