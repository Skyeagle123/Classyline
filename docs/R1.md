## Pending reservations (S1)

The owner selected **30 minutes**. New pending COD and WhatsApp orders expire at
`created_at + 1800`. Migration `0002_checkout_recovery.sql` backfills this deadline
for existing pending orders without deleting evidence. Apply migrations 0001 then
0002 to a separately authorized staging database; no remote migration was run.
Previously accepted formatted phone numbers are normalized for admission checks;
unrecognizable legacy numbers are retained for manual review.

Catalog reads, order submission/recovery, and authenticated admin order reads/status
changes sweep expired pending orders. A conditional SQL update cancels them with
`cancellation_reason=expired`; the existing cancellation trigger restores stock once.
No background infrastructure is required. On an idle store the stored state is swept
on the next relevant request. Confirmation racing expiry is rejected by a DB trigger;
confirmed orders do not expire. Expired keys recover the cancelled receipt and never
reserve again. Opening/sending a WhatsApp link is not merchant confirmation.

Abuse controls retain 15 new attempts per IP/15 minutes and add 3 attempts per
normalized phone/15 minutes, 100 attempts store-wide/15 minutes, and a transactional
one-pending-order-per-phone admission guard. Same-key saved receipts bypass these
new-order counters. These controls bound admission and rotation across IPs; they do
not prove ownership of a phone or provide human/bot verification. Distributed bots
can still consume admission capacity; public production needs separate abuse review.

## Fulfilment details (F1)

Authenticated `/api/admin/orders` includes persisted line snapshots: variant ID,
title, size, color, unit USD cents and quantity, grouped under the original order.
The UI shows unit/line amounts and cancellation/expiry context. Catalog edits never
rewrite historical order lines. Public order recovery omits customer contact data.

## Durable checkout recovery (F2)

The exact submission payload/key is written before POST. The cross-tab localStorage
entry contains only a random UUID key; temporary customer details live in this tab's
sessionStorage, cleared after receipt recovery or resolution. Web Locks serialize
submissions and recovery across tabs. Unsupported locks or storage failures fail
closed before submission. Network requests are abortable after 20 seconds; an abort
does not imply that the server failed to save the order.

On reopening the bag, POST `/api/orders/recover` with `{key}`. Its atomic batch retires
the key and reads the saved order. If saved, return its safe receipt. If absent,
return `{not_created:true}`; a DB trigger rejects any delayed original insertion.
Recovery never creates an order. Repeated recovery is safe; missing attempts remain
retired durably. Keep retired keys as long as delayed/replayed original submissions
must remain rejected; do not purge them independently of an approved attempt lifecycle.

A saved receipt keeps its durable key until the customer chooses Continue shopping,
so a reload between receipt delivery and cart clearing cannot produce a duplicate.
An unresolved attempt blocks replacements even if the user edits the form/cart.
Recovery also works when tab payload is missing or malformed, using only the key.
The recovery UUID is a bearer capability for the receipt and must not be logged or
placed in URLs. It reveals no name, phone or address. Recovery is same-origin JSON
and limited to 30 attempts per IP/15 minutes. No WhatsApp message is sent by code.

## Phone syntax (F3)

Accept Lebanese local numbers with 7–8 digits (optional national zero on 8-digit
forms) or explicit international `+`/`00` numbers with 8–15 digits. Strip spaces,
parentheses and hyphens; store canonical `+` international syntax. Lebanese `+961`
forms normalize a national zero and require a 7–8 digit national part. Reject
digit-free input, letters/control characters, malformed plus signs, and invalid
lengths. This is syntax normalization, not allocation/reachability verification.

## Verification and isolation

Regression tests cover deadlines, exactly-once stock restoration, confirmation and
submission races, migration preservation, phone/global admission, authenticated
snapshot reads, phone normalization, lost responses/reloads, delayed originals,
cross-tab serialization and fail-closed storage/network behavior. Tests use local
SQLite and synthetic data. Pages/D1 runtime and browser/device QA remain staging
checks. No infrastructure, production data, AI Agent resources or live integrations
are used by this remediation.
